En este caso **no conviene tratarlo como una migración “normal” de pantalla**, sino como una **migración funcional de producto** con cuatro ejes simultáneos:

1.  **Cambio de arquitectura UI**: NiceGUI mezclaba UI + lógica; React/FastAPI exige separación estricta.
2.  **Cambio de motor documental**: `pdfplumber + fitz` desaparecen y entra `docling`.
3.  **Cambio de contrato**: la UI ya no debe consumir texto plano dual, sino `ExtractedDocument`.
4.  **Cambio de interacción**: el wizard/focus mode no será 100% “form automatizable”; hay que modelarlo como **máquina de estados + contratos de fase**.

Mi conclusión principal es esta:

> **La automatización del frontend será alta para formularios, hooks, tipos, mutaciones y polling; pero parcial para el wizard/focus mode, que debe diseñarse como una experiencia React específica sobre contratos estables.**

***

# 1. Diagnóstico de la situación actual

En el legacy, `extraction_page.py` ya apunta a una arquitectura de tres modos: `library`, `design` y `execution`, con estados como `ExtractionState`, `DesignState` y `ExecutionState`. También conserva lógica de progreso por fases mediante `PHASE_RANGES`, con rangos como preparación, generación, ejecución, validación, refinamiento y finalización. 
Además, la capa de servicio legacy contiene todavía acoplamientos importantes: acceso a BD, sandbox, auditoría, cliente Brain, lectura dual de PDF mediante `extraer_texto_dual` y `PdfReaderDual`, generación de contratos UI y lógica de validación/extracción en el mismo módulo. [\[ujies-my.s...epoint.com\]](https://ujies-my.sharepoint.com/personal/fabra_uji_es/Documents/Archivos%20de%20chat%20de%20Microsoft%C2%A0Copilot/extraction_service.py)

El plan de Fase 2 ya identifica correctamente que la migración NiceGUI→React/FastAPI debe aplicar una regla de separación: BD, LLM, lectura/escritura de ficheros, máquinas de estado persistidas, servicios de automatización y validaciones estructurales deben ir a FastAPI; mientras que layout, pestañas, drawer, selección actual y estado visual deben quedar en React.

Por tanto, la migración del extractor PDF no debe hacerse copiando la pantalla legacy, sino **redefiniendo el dominio de extracción como API de backend y dejando React como orquestador visual**.

# 2. Riesgos principales

## Riesgo 1 — Intentar automatizar demasiado el wizard

Los formularios simples sí son muy automatizables con OpenAPI + Orval + Zod. Pero un wizard con focus mode, fases, previsualizaciones, polling, feedback humano, generación de script y refinamiento no es simplemente un formulario.

La parte automatizable será:

*   tipos de request/response,
*   hooks de subida,
*   hooks de polling,
*   mutaciones por fase,
*   validación básica de formularios,
*   contratos de errores,
*   componentes de campos dinámicos.

La parte que requiere diseño manual será:

*   navegación entre fases,
*   UX de focus mode,
*   stepper,
*   paneles contextuales,
*   preview de markdown/tablas,
*   interacción Copilot/Data Pills,
*   decisiones de habilitar/deshabilitar fases.

Esto encaja con el propio plan 9.13, que define una UI React con `PdfExtractPage`, `PdfExtractRun`, `PdfDropzone`, `ExtractionPhaseStepper`, `FieldSelector`, `ExtractedDataTable`, `RefineFeedbackPanel`, `GeneratedScriptViewer` y `useExtractionRun`. 

***

## Riesgo 2 — Migrar la UI antes de estabilizar Docling

Este sería el error más caro.

El plan ya advierte que **9.12b debe ejecutarse antes de 9.13**, porque el contrato cambia radicalmente: antes se usaban `texto_fitz` y `texto_plumber`; después la UI debe consumir `ExtractedDocument` con markdown, páginas y tablas estructuradas.

Por tanto:

> No debe empezarse la UI del extractor hasta que el backend Docling esté verde, con contrato OpenAPI estable y cliente frontend generado.

***

## Riesgo 3 — Prompts LLM obsoletos

El servicio legacy construía documentos para el LLM desde dos lecturas de PDF. Ahora el prompt debe cambiar de enfoque: ya no hay dos textos alternativos, sino:

*   `document.markdown`,
*   `pages[].markdown`,
*   `pages[].plain_text`,
*   `tables[]`,
*   metadatos de página,
*   posible estrategia `text_linear` o `complex_tables`.

El plan 9.12b ya especifica que los prompts deben pasar de `{texto_fitz}` y `{texto_plumber}` a `{markdown}` y `{tables_json}`. 
Esto implica que la migración no es solo técnica: hay que hacer una **batería TDD de prompts** con snapshots o fixtures de documentos.

# 4. Decisión sobre wizard/focus mode

Mi propuesta es:

## Mantener el concepto de wizard

Sí, porque la extracción tiene fases naturales:

```text
1. Subir PDF
2. Descubrir estructura
3. Seleccionar campos
4. Extraer
5. Refinar
6. Generar script
7. Guardar/publicar extractor
```

## Pero implementarlo como state machine ligera

No lo implementaría como “formulario gigante”.

Usaría algo parecido a:

```ts
type ExtractionPhase =
  | 'uploading'
  | 'discover'
  | 'select_fields'
  | 'extract'
  | 'refine'
  | 'generate_script'
  | 'done'
  | 'error'
```

La fuente de verdad de progreso debe ser el backend; React solo deriva qué panel mostrar.

## Focus mode sí, pero como patrón reutilizable

El extractor debe reutilizar el Focus Mode de 9.12a: sidebar colapsado, drawer contextual y tabs `Configuración`, `Data Pills`, `Copilot`. El plan ya indica que el extractor original tenía un wizard en pantalla completa similar al focus mode de flujos y que en React se replica al entrar al detalle del run.

| Focus mode               |                  Media | Reutilizar patrón 9.12a            |
| Preview markdown/tablas  |                  Media | Componentes manuales               |
| Prompts LLM              |             Baja-media | Backend + snapshots TDD            |
| Generación de script     |             Baja-media | Backend + tests de seguridad       |
| UI completa autogenerada |                   Baja | No recomendable                    |

# 8. Recomendación práctica

Yo no intentaría “automatizar el wizard”. Intentaría **automatizar todo lo que rodea al wizard**:

*   contratos,
*   tipos,
*   hooks,
*   mutaciones,
*   validaciones,
*   errores,
*   polling,
*   tests,
*   CI.

Y diseñaría manualmente una buena experiencia React para el flujo.

La migración debe empezar por el backend Docling porque cambia la forma misma del documento que consume el LLM. Si se construye primero la UI sobre la API vieja, se duplicará trabajo. El propio plan ya lo expresa: Docling cambia radicalmente el contrato y debe preceder a la UI.
