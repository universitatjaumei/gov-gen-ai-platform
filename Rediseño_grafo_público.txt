# PROMPT 0 — Contexto de Plataforma y Objetivo del Rediseño del Grafo Público

Actúa como **agente de programación senior** (Python + FastAPI + SQLAlchemy async + LangGraph + RAG).
Tu misión es diseñar e implementar una **arquitectura de grafo público extensible** para una **plataforma multi‑organización**
(universidades, ayuntamientos u otras instituciones), manteniendo un enfoque **determinista‑first**, TDD (RED/GREEN),
y reutilización máxima de componentes.

El objetivo NO es implementar un único chatbot, sino una **plataforma** capaz de soportar **múltiples chatbots públicos**
con **hipótesis de uso distintas**, **estrategias de retrieval distintas**, y **configuración en cascada**,
sin acoplar la topología del grafo a un único dominio.

---

## 0.1 Visión de Plataforma (principios no negociables)

1) **Multi‑organización, multi‑chatbot**
- Habrá múltiples organizaciones (tenants).
- Cada organización podrá tener uno o más **chatbots o portales públicos**.
- Cada chatbot representa un **caso de uso concreto** (no un “estilo” de organización).

2) **Casos de uso heterogéneos**
Ejemplos no exhaustivos:
- Normativa y procedimientos administrativos.
- Grupos de investigación (directorios, líneas, proyectos, contacto).
- Oferta académica (grados, másteres, doctorado, requisitos, calendarios).
- FAQs institucionales o municipales, servicios ciudadanos, portales temáticos.

3) **No grafo monolítico**
- No se debe implementar un único grafo “gigante” con condicionales por dominio.
- Se debe diseñar:
  - un **CoreGraph** reutilizable (orquestación común),
  - un **contrato de perfiles de grafo** (Graph Profiles) seleccionables por chatbot/portal,
  - un **contrato de estrategias** (Strategy Pattern) enchufables.

4) **Separación clara de responsabilidades**
- El **CoreGraph** define el flujo común (idioma, retrieval, generación, calidad, fallback, logging).
- El **GraphProfile** define la topología lógica y el UX (agregación, router, plantilla de respuesta, etc.).
- El **retrieval_mode** define **cómo se recupera la evidencia**, sin cambiar el grafo.

---

## 0.2 Estrategias de Retrieval (eje independiente)

La plataforma debe soportar **tres estrategias de retrieval**, seleccionables por chatbot/portal:

- `RAG`  
  Retrieval vectorial clásico (chunks, scoring, reranking opcional).

- `MD_LONG_CONTEXT`  
  Documentos Markdown + construcción de contexto largo (document packs).

- `MD_AGENT_SELECTOR`  
  Documentos Markdown + agente que selecciona qué documentos/secciones usar.

Principios:
- **No se deben crear grafos distintos solo por la estrategia de retrieval**.
- Todas las estrategias deben implementar un **contrato común de evidencia**
  (fuentes, contenido usado, idioma dominante, trazabilidad).
- El CoreGraph debe ser **agnóstico** a cómo se obtuvo la evidencia.
- La selección de la estrategia se hace mediante `retrieval_mode`
  y una `RetrievalPipelineFactory`.

---

## 0.3 Configuración en Cascada (defaults, no restricciones)

La plataforma aplica **cascada de configuración**, pero **no restringe perfiles ni modos**:

1) **Plataforma**: defaults globales.
2) **Organización**: defaults del tenant (idioma, thresholds, retrieval_mode por defecto, etc.).
3) **Chatbot/Portal**: overrides específicos.

Importante:
- **No existe** lista de “perfiles permitidos” por organización.
- El perfil y el retrieval_mode se eligen **por chatbot/uso**, no por organización.

---

## 0.4 Caso piloto inicial (Normativa + Procedimientos, estilo UJI)

Este es **un perfil concreto**, no “el grafo de la plataforma”.

Características del caso:
- Un **único widget público**.
- Dos dominios relacionados:
  - Normativa (base jurídica).
  - Procedimientos (operativa: pasos, plazos, formularios).
- El comportamiento deseado es **agregar**:
  - procedimiento + normativa aplicable cuando exista,
  - normativa sola cuando no haya procedimiento.

Idioma:
- Usuarios preguntan mayoritariamente en castellano.
- Evidencias frecuentemente en valenciano; algunas traducidas.
- La URL no identifica el idioma del contenido.
- Se requiere:
  - **preferencia de idioma**, no filtro estricto por defecto,
  - aviso de traducción solo si el idioma real de la evidencia difiere del idioma del usuario.

Este caso se implementará como un **GraphProfile específico**
(p. ej. `PUBLIC_PORTAL_AGGREGATOR`).

---

## 0.5 Objetivo arquitectónico

Diseñar e implementar:

### CoreGraph (siempre igual)
- detect_language
- retrieve (delegado a RetrievalStrategy + RetrievalPipeline)
- merge (según perfil)
- rerank (opcional)
- generate_answer (plantilla según perfil)
- quality_gate (faithfulness + relevance)
- fallback_response honesto
- log_interaction

### GraphProfiles (por chatbot/portal)
Ejemplos iniciales:
- `PUBLIC_KB_RICH`  
  Perfil genérico RAG para la mayoría de casos (grupos, oferta académica inicial, FAQs).
- `PUBLIC_PORTAL_AGGREGATOR`  
  Perfil específico que agrega múltiples fuentes (normativa + procedimientos).

### RetrievalPipelineFactory
- Selecciona pipeline según `retrieval_mode`.
- Garantiza contrato común de salida para todas las estrategias.

---

## 0.6 Restricciones y control de alcance

- No introducir thin client, ejecución local, expedientes ni automatización avanzada.
- No exigir que el usuario conozca identificadores internos (p. ej. códigos de procedimiento).
- No acoplar el CoreGraph a ningún dominio concreto.
- La lógica transversal (idioma, calidad, fallback, logging) vive en el CoreGraph.
- La lógica específica vive en perfiles y estrategias.

---

## 0.7 Entregables esperados

1) Librería de grafos públicos con:
   - CoreGraph
   - GraphProfiles
   - Estrategias enchufables
   - RetrievalPipelineFactory

2) Modelo de configuración con:
   - `public_graph_profile`
   - `retrieval_mode`
   - políticas (idioma, thresholds, reranker, plantillas)

3) Tests:
   - tests de contrato de retrieval pipelines,
   - tests de contrato de perfiles,
   - tests de integración del CoreGraph.
